<objective>
Fix the Phase 04 UAT blocker (UAT Test 2, major): the role edit form renders ZERO editable fields, which transitively blocked UAT Tests 3, 4, and 5 (no form to submit).

Root cause (diagnosed, HIGH confidence, reproduced — see `.planning/debug/edit-form-no-fields.md`): `MatchSchema` in `Pages/Roles/Edit.cshtml.cs` selects the role's schema row by `DetailModel.GetSkills(detail).FirstOrDefault()` — i.e. `__Skills[0]`. But `__Skills` is built from `Type.GetInterfaces()` (`Backlot.Core/Loader.cs:280-296`), which lists inherited base markers (Persist, Permission, Role, Uid) FIRST and appends the role's own concrete name LAST. So `__Skills[0]` is e.g. "Persist", while the `director/roles` schema rows are keyed by the concrete role name (`role.GetRoleName()`, e.g. "Message", per `Backlot.Defaults/Scenarios/Configuration/Roles.cs:21-23`). The match returns null → `Schema` is null → `Edit.cshtml` renders the "Nothing to edit" empty state. The identical broken match runs on `OnPostAsync` (line 97), so Save is also broken once the form renders.

Fix strategy: select the schema row by a skill that actually appears as `schema.Role`. The role's own/most-derived name is the LAST element of `__Skills`; matching base markers first risks binding the wrong contract. So `MatchSchema` walks `__Skills` from most-derived (last) to least-derived (first) and returns the FIRST skill that has a matching schema row, returning null only when no `__Skills` value matches any `schema.Role`. This is applied to both `OnGetAsync` and `OnPostAsync` (they share the one `MatchSchema` method, so a single fix covers both paths). The fix is purely in the match key — the schema field list, coercion, payload build, and persist paths are unchanged and already correct.

WR-06 reconciliation: WR-06 ("match the primary skill ONLY — do not fall back to secondary skills, so guessing from a later skill cannot write fields under the wrong role contract") was written on the FALSE premise that `__Skills[0]` is the role's own type. The premise is wrong (`__Skills[0]` is a base marker), which is exactly why the form never renders. WR-06's underlying GOAL — bind exactly one deterministic schema row and never silently edit the wrong field set — is preserved: the new `MatchSchema` still resolves to exactly one row, prefers the role's OWN/most-derived contract, and returns null (explicit "no schema" state) when nothing matches. We reconcile WR-06 by correcting its mechanism (most-derived skill that has a schema row) while keeping its anti-mismatch intent. This reconciliation is documented in the method comment and in EDIT-01's traceability.

Empty-state copy: `Backlot.Defaults/Scenarios/Configuration/Roles.cs:82-89` filters the schema list for non-admin users down to roles used in scenarios the user can access. So a null `Schema` has two distinct causes: (a) the role's schema row is filtered out of the response for THIS user (visibility), or (b) the schema matched but has no editable fields. Improve the empty-state copy to distinguish "no schema row is visible to you for this role" from "this role has no editable fields", so an operator understands whether it is a permission/visibility limitation or a genuinely field-less role.

Why this slipped through: the original Phase 04 verification (`04-VERIFICATION.md`) only did a code-read ("primary-skill-only schema match (WR-06) — is correct by read"). A code-read cannot catch a runtime ordering assumption. This plan therefore includes a deterministic harness for the match logic AND a blocking human-verify checkpoint that re-runs UAT Tests 2-5 against a live authenticated edit page.

Purpose: Restore the editable form so UAT Tests 2-5 pass and EDIT-01/02/03 are genuinely satisfied at runtime, not just by read.
Output: `Pages/Roles/Edit.cshtml.cs` with a corrected `MatchSchema`; `Pages/Roles/Edit.cshtml` with disambiguated empty-state copy; `Pages/Roles/Detail.cshtml.cs` `GetPageTitle` aligned to the same most-derived-skill selection.
