<objective>
Fix the Phase 04 UAT blocker: the Edit button on a role detail page is permanently disabled, which also blocks UAT Tests 2 and 3.

Root cause (diagnosed, high confidence — see `.planning/debug/edit-button-disabled-detail.md`): the Backlot `seekbase/detail` scenario returns the role nested under a `Role` wrapper — `{ "Role": { …flattened role incl. __Permission, __Skills, __LastModifiedDate… }, "Relations": [...] }`. Studio's `DetailModel.GetPermissions` / `GetSkills` / `GetNonSystemFields` / `GetPageTitle` and the Edit page's server-side `CanWrite` gate all read `__Permission` (and friends) at the TOP level of the response Body, where they do not exist. `TryGetProperty("__Permission", …)` fails, `CanWrite` defaults to `false`, and `Detail.cshtml` renders the disabled Edit button. The same mismatch starves skills/fields/title and would 422 the Edit page if reached directly.

Fix strategy: unwrap once, at the single chokepoint. All three call sites (`Detail.OnGetAsync`, `Edit.OnGetAsync`, `Edit.OnPostAsync`) go through `IBacklotApiClient.GetRoleDetailAsync`. Performing the unwrap there fixes every consumer at once with no change to the PageModels, and keeps the unwrap logic in one place. The unwrap is DEFENSIVE: it only descends into `Role` when the top-level Body is an object that actually contains a `Role` object — so a future flat response shape (the live shape was never confirmed against a running, authenticated API) still works unchanged.

Purpose: Remove the blocker so the Edit button enables for writable roles and UAT Tests 1/2/3 become testable.
Output: `Services/BacklotApiClient.cs` with a defensive `UnwrapRoleDetail` helper applied inside `GetRoleDetailAsync`.
</objective>

  <action>
In `Services/BacklotApiClient.cs`, change `GetRoleDetailAsync` so the value it returns is the unwrapped role element rather than the raw envelope Body.

Currently `GetRoleDetailAsync` does:
- `var envelope = await PostEnvelopeAsync<JsonElement>("api/role/seekbase/detail", new { For = uid }, ct);`
- `return envelope?.Body;`

Replace the `return envelope?.Body;` line so that, when the envelope and its Body are present, it returns `UnwrapRoleDetail(envelope.Body)`; when the envelope is null, it returns `null` (preserve the existing nullable behavior — keep returning `JsonElement?`).

Add a new `private static JsonElement UnwrapRoleDetail(JsonElement body)` helper to the class implementing the defensive unwrap. The seekbase/detail scenario wraps the role as `{ "Role": {…flattened role…}, "Relations": [...] }`, so the role's `__Permission`, `__Skills`, `__LastModifiedDate`, and data fields live under `Body.Role`. The helper must:
- Return `body` unchanged if `body.ValueKind` is not `JsonValueKind.Object` (defensive: anything non-object passes through).
- If `body` is an object AND `body.TryGetProperty("Role", out var role)` succeeds AND `role.ValueKind == JsonValueKind.Object`, return `role.Clone()`.
- Otherwise return `body` unchanged (this is the future-flat-shape path — role fields already at the top level, no Role wrapper).

Use `role.Clone()` so the returned `JsonElement` stays valid after the parent `JsonDocument` from `ReadFromJsonAsync<ApiEnvelope<JsonElement>>` is disposed. (`PostEnvelopeAsync` deserializes into `ApiEnvelope<JsonElement>`; the inner JsonElement is backed by a JsonDocument whose lifetime ends with the call. Cloning detaches the sub-tree so callers can read it safely.)

Keep the existing XML doc/comment on `GetRoleDetailAsync` and extend it to note that the returned element is the unwrapped role (Body.Role when the wrapper is present, else Body), so all PageModel helpers (`DetailModel.GetPermissions`/`GetSkills`/`GetNonSystemFields`/`GetPageTitle` and the Edit-page CanWrite gate + field seeding) read at the correct level. Do NOT change the method signature, the interface `IBacklotApiClient`, or any PageModel — the fix is contained to this single chokepoint.
